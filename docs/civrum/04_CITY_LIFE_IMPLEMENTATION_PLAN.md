# NEXCIV City 生活模拟实施规划

2026-11-26 · 实施提案 · 对应生活模拟设计 V1.2

首个可试玩版本交付一段会留下后续的城市生活。玩家用自己的 Harness 驱动一名居民，在咖啡街收到玩家递来的纸条，采访常驻 NPC，发布一篇有来源的《城邦早报》。下一次相遇时，NPC 的反应受到上次交流影响。玩家可以从明信片返回这段故事。

MCP 和 HTTP API 共用城市服务。玩家承担自己的模型推理费用，平台承担城市服务、存储、排队、规则模拟和内容管理费用。首发建议用三名全城共享的规则 NPC，咖啡摊主、观察员和常客各有明确偏好。首发体验无需平台调用模型。

## 首版产品范围

### 可运行的咖啡街规则试玩（E3-05）

通过街区观察页的「观察咖啡街」进入 `/nexciv-preview/cafe`。01 号在街角帮工，收工后根据附近的人、自己的精力和收到的建议选择行动。可观察邀约、散步和休息，也可在工作期间递「去北岸钓鱼」的纸条。新的纸条会覆盖尚未执行的建议。

钓鱼复用通往北岸码头的步行路线。试玩把路程快进为 64 秒，整轮约 1 分半钟。Agent 到达钓位并有足够精力后，才能抛竿、等浮漂和收线。服务端按本班次结算一次结果，可能空竿，也可能钓到一条小鱼并放回。结果写入本次经过，关页期间照常结算。

班次结束后可在同一浏览器选「再看一个班次」。阿禾会记住最近一次实际交谈或婉拒，收工后主动接话，当前忙碌时仍有可能改约。单独休息或钓鱼的班次不会覆盖上一次会面。台词记录包含上一班次的开班时间和会面结果。浏览器的试玩会话有效期为 30 天，开新班次时清理 30 天前的记录。

试玩使用现有居民与街景、规则决策和独立 SQLite 数据库。运行需要支持 `node:sqlite` 的 Node.js 22.13+。开发环境默认写入 Web 应用工作目录的 `cache/nexciv-cafe-v1.sqlite`，服务保持运行时按时推进，进程中断后根据持久化截止时间补算。正式构建默认关闭试玩 API，单机演示可显式设置 `NEXCIV_CAFE_DEMO_DB` 为专用数据库路径。共享城市、外部 Harness 和正式 PostgreSQL/BullMQ 接入仍属于后续里程碑。

同一入口可选择「城邦观察员」，采访议题为「北岸码头傍晚要不要加灯？」。准备阶段可用纸条建议优先采访阿禾或码头常客，也可选择先问可见度或加灯的影响。阿禾忙碌时，01 号根据本次建议及之前的会面决定等待或先去码头。受访者回答后，服务端保存独立的来源记录，包含人物、地点、完成时间、问题和原话。玩家可从班次经过打开对应原话，关页期间照常推进。

观察员收到两位居民的回答后，服务端按已保存的采访记录排成一期《城邦早报》。每个班次只出一期，报道引用可定位到原话、采访地点和时间。进入「阅读《城邦早报》」可读本浏览器的历期报道，已完成的旧班次也可补刊。记录随试玩班次保留 30 天。版面标明 `AI SIMULATED · DEMO`，公开发布及审核仍按后续里程碑实施。

回访同一浏览器时，咖啡街会按上次在前台看到的时间点生成一张明信片。明信片显示当前班次新增的活动，最多列出最近三条，可打开完整经过。如果其间已有新一期早报出刊，可以直接进入对应期刊。离开页面或标签页切到后台时，服务器仍推进活动。没有新进展时，页面保留最近的班次记录。

本地外部 Agent 验证使用 `scripts/nexciv-observer-harness.mjs`，通过咖啡街 HTTP 服务开一个独立观察员班次。脚本读取 `NEXCIV_MODEL_BASE_URL` 和 `NEXCIV_MODEL`，密钥通过终端隐藏输入或 `NEXCIV_MODEL_API_KEY` 传入。外部 Agent 可根据当前观测选择采访阿禾、等待她或先去北岸。服务器校验班次、可用动作和回执，完成已接受的采访行程，并在两位居民回答后出刊。

本地 MCP 试玩使用 `scripts/nexciv-observer-mcp.mjs`。依赖安装后，从项目目录注册：

```powershell
$nexcivNode = (Get-Command node).Source
$nexcivMcp = (Resolve-Path 'scripts/nexciv-observer-mcp.mjs').Path
codex mcp add nexciv -- $nexcivNode $nexcivMcp
codex mcp get nexciv
```

在本机咖啡街打开「连接 Agent」，生成配对码，把复制的配对指令发给已加载 `nexciv` 的 Codex 会话。配对码 5 分钟内有效，使用一次后失效。`pair_browser` 兑换只绑定当前浏览器试玩的凭据。让 Agent 用 `start_observer`、`observe_observer`、`choose_interview`、`read_shift` 和 `read_newspaper` 完成采访，网页显示同一个班次和同一期早报。配对凭据有效期为 24 小时，网页点击「断开 Agent」可立即撤销。已接受的行程继续由城市推进，后续 MCP 请求需重新配对。

城市服务默认使用 `http://127.0.0.1:3137`，本机其他端口可通过 `NEXCIV_DEMO_URL` 指定。首次配对前，MCP 仍可使用独立试玩会话。独立会话保存在忽略目录 `cache/nexciv-observer-mcp.session`，配对凭据保存在同路径加 `.pairing` 后缀的文件中，服务端 SQLite 仅保存凭据的哈希。模型由 MCP 客户端提供。正式居民认领和远程 MCP 按后续里程碑实施。

同一次配对也支持全城试走。`list_city_places` 返回地点 ID、步道范围和入口坐标，`observe_city` 返回当前行程、落点和可用状态，`move_to` 接受 `{ place: "works" }` 或 `{ x: 12.6, z: 71.5 }`。地点共用 `public/nexciv-walk` 的室外步道路网。坐标使用米，由服务端投影到 0.75 米以内的已测绘步道，超出步道范围会拒绝。试走使用 4 米/秒的演示速度，行程和落点随同一试玩会话保存，网页跟随镜头与文字进度读取同一条路线。可先后前往任意已连通地点。自由试走和观察员班次交替执行，在外完成行程后回咖啡摊即可开班。

到达公共建设中心入口附近后，`observe_city` 会返回现场管理员、入口等候区、巡查路线和可选动作。Agent 将其中一个动作 ID 交给 `interact_city`。它可以询问管理员并读到预设回话、等候休息恢复精力，或接下巡查，沿同一套步道到访两个点位后返回。服务端按到访时刻逐条公开巡查记录，结果保存在本地试玩会话里。活动完成后再选下一项或离开。网页与 MCP 可读取最近六条现场活动，刷新或断开连接后已受理的活动继续推进。

到达议会大厅前庭后，可通过 `interact_city(actionId: "governance.read")` 查看议事公告。01 号沿已测绘步道走到东侧公告栏，停下阅读后把标有 `DEMO` 的议程写入活动记录。网页跟拍和 MCP 使用同一行程。读完后角色留在公告栏旁，接下来的行程从那里出发。

读完后，01 号可选择 `governance.survey` 调研湖畔路灯。服务端沿已测绘步道安排两个观察点和回程，网页会在每个点停步转向现场。观察结果在停留结束后进入活动记录。回到公告栏解锁 `governance.submit`，报告引用两条已记录的观察。提交后，本地试玩会话中的公告栏显示「已收到调研报告」，报告标为 `DEMO`。

| 角色 | 能做的事 | 可见结果 |
| --- | --- | --- |
| 访客 | 浏览城区、公开早报和公开动态 | 点开一篇早报，沿来源找到发生了什么 |
| 玩家 | 通过受邀站内账号认领一名链下居民，授权 Harness，观察活动，递纸条，暂停或撤销接入 | 看见纸条的处理结果，读自己的明信片和最近活动 |
| 玩家 Agent | 读取自己的可见信息，提出移动、邀请、回应、发言、接任务和交稿请求 | 被城市规则接受的动作改变活动进度和后续关系 |
| 常驻 NPC | 按偏好、精力、当前场合和过去互动选择动作 | 能主动打招呼、答应、拒绝或提出条件，并在后续互动中记住发生过的事 |
| 注册公民 | 用持有 Agent ID 的钱包参与现有正式治理和公共建设 | 查阅已确认的投票、贡献和施工进度 |

首个故事使用咖啡街与中央广场两个现有区域。每天发布一个有分歧的公共话题，例如广场的晚间活动安排。咖啡摊承担见面和休息点位，城邦观察员是唯一首发职业。一篇早报引用至少一条已发布的城市事件。玩家回访时可看到早报、一次关系变化及其来源。精力和心情可驱动少量行为变化，人气 `Fame` 随后按公开互动规则引入。

首版之后优先从社交反馈、第二份职业和周榜大屏中选择已被试玩数据支持的方向。消费、打赏、派系、多区生活和更多 NPC 随后再立项。网页 BYOK 移出当前规划，模型供应商账号和密钥由玩家的 Harness 管理。

## MCP 和 HTTP API 契约

城市服务是动作和结果的权威。Harness 在玩家自己的环境决定下一步，调用 MCP 工具或 HTTP API。两个适配入口交给同一个应用服务处理权限、校验、执行和结果，网页也使用同一领域规则。

| 能力 | MCP 工具候选 | HTTP API 候选 | 数据和权限 |
| --- | --- | --- | --- |
| 观察 | `observe_city` | `GET /api/v1/city/observation` | 基于 `AgentObservationV1` 裁剪可见的场所、事件和可用动作，携带修订版本 |
| 收件 | `read_inbox` | `GET /api/v1/city/inbox?cursor=…` | 只返回授权居民的纸条、邀请、回复与结果，支持游标续读和过期提示 |
| 提交动作 | `submit_action` | `POST /api/v1/city/actions` | 携带 `requestId`、动作类型和参数。回合动作附会话版本。返回回执 ID 和受理状态 |
| 查询结果 | `get_action_result` | `GET /api/v1/city/actions/:id` | 只返回获授权的回执、执行结论和可读原因。结果也可由收件箱续读 |

首批动作覆盖前往固定点位、邀请、接受或拒绝、按回合发言、接受观察员任务、提交早报。返回 `ACCEPTED` 仅表示请求受理，后续结果区分完成、失败、超时或撤销。命令回执与正式链上交易使用各自的状态。客户端提交同一 `requestId` 和相同内容时读回原回执。相同 ID 携带不同内容时返回冲突。

远程 MCP 按目标 Harness 实测的协议版本使用 Streamable HTTP 和适用的授权规范。HTTP API 可用独立、可撤销的应用凭据。由服务器从凭据确定居民归属和读写范围。浏览器会话负责确认认领、授权、暂停和撤销。MCP、API 和浏览器按相同规则校验越权、当前回合、内容长度和频率。正式提案、投票及贡献继续由符合资格的 owner 直接使用钱包处理。 [MCP 传输规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) · [MCP 授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

首个接入样例同时提供 HTTP 脚本和一个实测 Harness 的配置。样例从环境读取城市访问凭据，合法动作和结果由脚本可重放验证。平台日志只记录所需的请求、回执和错误信息，可按回执排查动作，并限制凭据及私人消息的可见范围。

## 活动和城市状态

活动以后台事件推进。公开位置由获准的移动和到达记录投影到场景，网页根据投影插值。接近玩家时可以增加动画细节，后台始终使用同一套到达、对话、工作和结算规则。纸条送达和审核后的公开发言通过各自的事件流呈现，60 秒视觉 tick 继续负责世界表现。

| 事件 | 服务端行为 | 玩家看到的结果 |
| --- | --- | --- |
| 符合条件的邀请 | 创建唯一会话，记录发起者、收件人和过期时间 | 对方待回应、接受、拒绝、提出条件或超时 |
| 一方发言 | 校验轮次、地点、双方状态和内容。通过审核后才进入公开动态 | 可定位到实际事件的气泡或对话列表 |
| 玩家递纸条 | 写入私有收件箱，标注相关会话和有效轮次。Harness 可另行提交自己的回复，回复走公开内容审核 | 立即看到已送达，后续看到采纳、改写、略过或过期 |
| 任务完成 | 校验活动归属、完成条件和公开来源。发布事件与完成标记在同一事务提交 | 同一任务只出现一次完成记录。审核通过的早报可阅读 |
| 更新关系 | 分别更新 A 对 B 和 B 对 A 的记录，并保留触发事件 | 下次见面可基于这段经历改变态度。公开展示范围按可见性规则控制 |

网页关闭时，在线的 Harness 可以继续访问城市。Harness 断开时，服务器推进已接受的规则动作，处理超时，保留可恢复的收件和活动。需要模型的发言、采访判断和写稿停在等待状态，首版按任务期限恢复或结束。新连接通过游标读取积压事件，重新观察当前状态再行动。玩家被暂停、已撤销授权或落后于会话修订版本时，服务拒绝相应写入。

平台用 PostgreSQL 保存居民归属、活动、会话、关系、收件、稿件和回执。状态更新与事件提交以事务为边界。Worker 通过现有 Redis/BullMQ 架构投递定时和到期处理，使用业务记录判断是否已经推进。服务重启后从持久状态补扫未处理步骤。队列重放、双端并发和网页重连都遵循同一套幂等约束。公开审核只投影允许展示的消息。早报清楚区分已发生的城市事件、引用的居民发言和作者观点。

## 首发 NPC 与内容

| NPC | 主动行为 | 第二次见面时可观察的变化 |
| --- | --- | --- |
| 咖啡摊主 | 在营业时段打招呼，按来客兴趣介绍一个公共话题 | 如果此前交流愉快，会主动提起上次话题或介绍一位当事人 |
| 观察员 | 主动追问来源，也可邀请附近居民补充记录 | 记得玩家是否提供了来源，并据此决定是否继续采访 |
| 广场常客 | 围绕一个明确的城市议题表达立场，按关系接受、婉拒或提出条件 | 上次存在分歧时会要求澄清，后续交流可改善或恶化关系 |

每个 NPC 采用可测试的偏好、冷却、有限回合与有条件台词。模板只引用角色可见的真实事件。冷启动时设置公开城市话题和 NPC 身份，测试环境用清晰标记的演示数据。NPC 身份、事件来源与玩家 Agent 都可辨识。规则也用于生成私有明信片的摘要，摘要链接至该玩家有权查看的事件。当天没有值得回访的互动时，展示最近活动即可。

## 分阶段交付和依赖

以下是建议投入，按一名主要开发者的工作日估算。阶段 0 至 4 约 16 至 22 个开发日可形成内部试玩，阶段 5 后约 20 至 28 个开发日可形成受邀测试版。区间基于现有场景复用和已有测试环境，真人钱包验证、外部接入审批和玩家回访观察周期独立计算。

| 阶段 | 预计投入 | 主责 | 依赖 | 交付与验收 |
| --- | --- | --- | --- | --- |
| 0 产品规则与契约 | 1–2 日 | 产品、领域 | 现有规划 | 确认居民认领、私有消息、公共事件、离线语义和 API 草案。给出连接、断开、暂停、撤销的验收案例。与现有规格有差异的项写入 ADR 计划 |
| 1 接入一名居民 | 3–4 日 | API、数据 | 0 | 在隔离环境办通账号认领、MCP、HTTP API 和访问凭据。目标 Harness 能观察并让居民走到指定点位。HTTP 样例能执行等价动作。跨居民访问与重复提交检查通过 |
| 2 一场有后续的会面 | 4–5 日 | Runtime、Worker | 1 | 三名规则 NPC、一条公共议题、一个完整会话和双向关系历史。中途断开、并发回应和服务重启后，活动从已保存的步骤推进 |
| 3 把会面变成玩家玩法 | 4–6 日 | Web/3D、Runtime | 2 | 咖啡街与广场的移动、点选、气泡、递纸条和等价 HTML。首个观察员任务可交付早报，读者能打开来源。玩家私人输入仅对授权方可见 |
| 4 离线与回访 | 4–5 日 | Worker、Web、测试 | 3 | 游标续读、到期处理、离线活动摘要和明信片。完成一次完整脚本化演练并记录平台玩家推理调用为零。内部玩家完成首段试玩 |
| 5 受邀测试与运营 | 4–6 日 | 全栈、产品 | 4 | 完成真实 MCP 客户端、HTTP、Web 和数据库故障回归。上线运营开关和监控，邀请小批玩家试用。用回访行为决定下一期方向 |

阶段 0 结束后可以并行整理角色台词、确定咖啡街与广场的点位，以及编写失败路径用例。第一条可见交付依赖阶段 1 的动作回执。早报和纸条采用阶段 2 的会话契约。正式公民治理继续按 `E1-00` 与 `E7-01` 的路径验收。生活模拟的近期工程从 `E3-05` 双 Agent 协作扩展，借鉴 `E3-07` 的动作日志和控制台。每次编码按主计划选定一个任务 ID 和文件范围，避免接入、游戏行为和渲染一起变更。 [任务依赖](../IMPLEMENTATION_PLAN.md#4-codex-任务-id-和依赖-dag)

## 试玩后的扩展顺序

扩展由试玩结果触发。接入频繁失败时先改授权和诊断指引。能顺利接入但故事引不起复访时，先改善事件内容以及玩家对角色的影响。首轮试玩出现稳定的重复互动后，再安排以下交付。

| 顺序 | 依赖 | 交付与验收 |
| --- | --- | --- |
| 公开反馈和人气 | 早报有人读，愿意追踪角色故事 | 早报点赞、公开回应和 `Fame`。同一玩家对同一内容只计算当下有效的一次点赞，撤销和重试结果一致 |
| 咖啡摊职业 | 玩家愿意在同一地点重复见面，基础会话可恢复 | 选饮品、短对话、交付。每次结束留下可追溯的饮品交付或关系事件。是否引入城内报酬由产品规则另定 |
| 周榜和塔楼 | 有稳定的公开互动，已确定排名依据和内容审核 | 记录可重放的周榜结算。塔楼读取已发布榜首和展示期。并列、无人获奖和审核未通过时有可解释的展示 |
| 更多居民和街区 | 已能测量待处理任务、数据库与接口负载 | 先按活跃居民负载测试，再逐步增加常驻 NPC 和点位。每轮扩展检查线上线下是否产生一致结果 |

## 验收和试玩判断

| 检查 | 通过条件 |
| --- | --- |
| 接入等价性 | 同一套动作向量分别经 MCP 和 HTTP API 得到相同校验、状态和事件形状。超期、撤销和跨居民访问按权限拒绝 |
| 活动一致性 | 同一请求并发重放或进程在提交前后重启，最终只有一次生效。每个发言轮次最多接受一条有效发言，离线续读有序 |
| 社交完整性 | NPC 能因上一次互动改变后续决定。早报能追到公开来源。私人纸条只在授权收件箱和玩家界面出现 |
| 成本归属 | 所有玩家模型调用由外部 Harness 发起。平台费用追踪覆盖接口、数据库、队列和规则 NPC。断开测试验证规则活动照常运行 |
| 场景与无障碍 | 3D 和 HTML 展示一致的活动来源。无 WebGL 可以读动态、递纸条和打开早报。演示事件和已确认链上事实都有明确来源 |
| 玩家体验 | 玩家完成连接，观察一场会面，主动递纸条，看到后续关系变化。回访时能从明信片找到早报或当事人 |

每阶段按变更运行 `pnpm lint`、`pnpm typecheck` 和对应 `pnpm test` 用例。世界投影变更运行 `pnpm test:world`。浏览器交互变更运行相关 Playwright 和落地后的烟测，环境满足时跑 `pnpm test:visual`、`pnpm test:responsive` 和 `pnpm test:a11y`。数据库并发与恢复用例使用隔离测试库。若后续涉及合约，再按合约规范运行 Foundry 与钱包真实验收。

首轮建议邀请 8 至 12 名愿意接入 Harness 的玩家，记录从认领到第一次成功动作的耗时、在首场对话中递纸条的人数、主动进行第二次互动的人数，以及第二天与第三天无人工提醒回访的人数。回访指标以完成首次体验的玩家为分母，连接失败另行记录。样本用来定位接入摩擦和故事体验，后续再用更大样本估计留存。如果玩家接不上，改善授权与接入指导。如果玩家能接入但首场后不回来，先调整故事和反馈，再扩展职业和大屏。

## 开工顺序与待确认事项

1. 先落阶段 0。按现有 `E3-05` 明确共享会话、公开事件和关系记录，并在实施前同步受影响的产品与世界规格。
2. 阶段 1 从一个目标 Harness 和一个 HTTP 测试脚本开始。固定第一个验收动作与最小观察数据，再建立鉴权、回执和重试用例。
3. 阶段 2 至 4 围绕同一段试玩故事推进。每阶段交付一条可重放记录，让 UI、3D 和自动化都能基于同一组事件验证。

开工建议默认邀请制、每账号一个链下居民、三个共享 NPC、简报发布审核和私有纸条。需要选定的项目决策是首测 Harness、生产登录方式，以及对外开放居民认领的时间。隔离环境可先验证动作和生命周期，正式开放前确认授权与产品规则。
